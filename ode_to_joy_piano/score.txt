# 《欢乐颂》单轨纯旋律（C 大调）—— OX-1 蓝牙曲谱文本文件
# ------------------------------------------------------------
# 来源：work/2026-10-29_timbre_candidates/melody_ode.py 的 **MELODY**
#       （= git commit 7c7293e 当年上板确认过的原版：P1+P2+P3+P2，
#         62 音 / 64 拍 / 32.0 s / BPM 120）
# ★ 音域：权威原版是 **E5 起步（比常规高一个八度）**；线上 DATA 帧的 bitmap
#   只有 24 bit ⇒ **键号必须 ≤ 23（B4）**。⇒ 本谱 **整体降一个八度**（调性不变，
#   仍是 C 大调）：E5→E4 … C5→C4 … G4→G3。降八度后键域 = G3(7) .. G4(19)，
#   全部落在 C3(0)..B4(23) 内 ⇒ **越界音（>23）数量 = 0**。
#
# 格式：`step key [dur]` —— tools/score_push.py 的 read_score_file 与网页端
#       OX1Score.parseTextScore 的**共同子集**（`#` 之后是注释）
#   step = 步号（0 起，单调递增，可有空洞）；key = 半音偏移（0=C3 … 23=B4）；
#   dur  = 持续步数（1..64，省略 = 1）。
# ★ 步长：**--step-ms 120** ⇒ 四分音符 = 4 步 = 480 ms ⇒ **BPM = 60000/480 = 125**。
#   （权威原版是 BPM 120 / Q=500 ms；若改用 `--step-ms 125` 即精确复现 BPM 120，
#     音符时值比完全相同：四分=4 步 / 八分=2 步 / 附点四分=6 步 / 全音符=8 步）
#   下发：py tools/score_push.py --file scores/ode_to_joy_piano.txt --step-ms 120 --loop 1
#
# ★ 本谱是**单轨纯旋律**：一行一音，没有任何和弦（key 之间用空格分隔、
#   不用 `+`），也没有伴奏轨。
# ★ 总步数 = 256（= 最后一个音的 step+dur；协议的 total_steps 上限 256，**恰好占满**）。
#   ⇒ **下发给 FPGA 的 HEAD.total_steps 必须是 256**（不是音数 62）。
# ★ 休止步 = 该步号**不出现**（文本格式无法表达 bitmap=0 的休止；
#   HEAD 会清空全部 256 个 slot，没写到的步 = valid=0 = 不发音）。
#
# ★★ ★★ ★★ 下发时的 total_steps 陷阱（实测，已确认）★★ ★★ ★★
#   tools/score_push.py 的 HEAD 用的是 **len(steps) = 事件个数 = 62**，
#   而本谱的**谱长是 256 步**（旋律天然有休止步：一个四分音符占 4 步，
#   但只有第 1 步有事件）。⇒ 两者差 194 步。
#   ⇒ 按 SPEC §2 的「`step` ≥ total_steps ⇒ 该事件被丢（ACK 0x04）」，
#     **本谱 62 个事件里有 47 个会被 FPGA 丢掉**（步号 ≥ 62 的全部），
#     只剩前 15 个音能响 ⇒ 旋律会被截断成一段噪声。
#   ⇒ **正确的 total_steps = max(step + dur) = 256**，本谱恰好用满协议上限。
#   ⇒ 两种修法（任选其一）：
#       (a) 修 score_push.py：把 `link.head(len(steps), ...)` 改成
#           `link.head(max(s + d for s, (_b, d) in steps.items()), ...)`
#           —— ★ 这是 score_push.py 的**真 bug**，不是本谱的问题；
#              单声部旋律/任何含休止的谱都会中招。
#       (b) 暂时用本谱的**演示版**（步号连续 ⇒ 两种口径一致）：
#           见交付报告。
#   ⇒ 本仓库的 tools/check_score_files.py 会把三口径并排打出来并告警。
